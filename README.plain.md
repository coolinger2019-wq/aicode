# Ming(明)编程语言 · 人话版

> 一句话:**Ming 想让你(和 AI 助手)写出来的代码,"是什么意思"就"只能是什么意思"——机器能检查,人也能看懂,不容易悄悄出错。**

**换语言:** [普通中文版](README.md) · [English](README.en.md) · **中文 · 人话版**

## 这是什么

Ming 是一门新的编程语言,专门为"AI 写代码 + 人来把关"这件事设计。

现在的 AI 写代码很快,但有一类错误特别多:类型悄悄转来转去、null 到处漏、数字溢出不出声、改了 A 结果 B 也变了……这些坑,人类语言背了几十年的包袱。Ming 的做法是:**把这些坑在语言层面直接挖掉**,而不是靠程序员自觉。

## 它把哪些坑挖掉了

- **不做偷偷的类型转换。** 是 `i32` 就是 `i32`,想变就得明说。
- **没有 null。** "可能没有值"必须写成 `Option[T]`,漏处理编译器会拦。
- **数字溢出、除以零、数组越界、Map 里没有这个键——全部当场报错**,带文件名、行号、列号和错误码,不会算出一个错的结果继续跑。
- **碰硬盘、碰网络,必须在函数签名里写清楚**(比如 `with io, fs`)。没写明就编译不过——"偷偷读文件"这种代码在 Ming 里写不出来。
- **赋值和传参都是拷贝。** 改一个变量不会连带改掉另一个,不会出现"我明明没动它"的怪事。
- **同样的代码,永远同样的结果。** 遍历顺序固定、求值顺序固定,测试可以放心复现。
- **AI 友好。** 所有工具都能输出 `--json`,报错带固定的错误码和修改建议,AI 可以"生成 → 检查 → 修改"自动循环。

## 看个例子

```ming
fn main() with io {
    let name = "世界";
    let mut total = 0;
    for i in 1..11 {
        total += i;
    }
    print("你好, \{name}! 1..11 的和是 \{total}");
}
```

跑起来:

```bash
$ node bin/ming.js run examples/hello.ming
你好, 世界! 1..11 的和是 55
```

让机器检查它:

```bash
$ node bin/ming.js check examples/hello.ming --json
{ "ok": true, "diagnostics": [] }
```

## 怎么试一试

只需要 Node.js 18 或更新版本,不用装任何第三方包:

```bash
node bin/ming.js run   examples/fizzbuzz.ming   # 运行
node bin/ming.js check 你的文件.ming --json      # 检查(给 AI 看的 JSON 版)
node bin/ming.js fmt   你的文件.ming --write     # 自动排版成唯一风格
node bin/ming.js cc    你的文件.ming             # 编译成原生程序(需要 gcc/clang)
```

## 现在的进度(实话实说)

Ming 还在 **v0.x 快速演进阶段**,不是 1.0,语义和工具会继续变。但"说过的话"都有测试撑着:

| 项目 | 现状 |
|------|------|
| 当前版本 | **v1.3.0**(2026-11-27) |
| 自动测试 | **1809 项全部通过** |
| 多引擎一致性 | 同一个程序会在好几套引擎上跑(解释器 / 字节码虚拟机 / WASM / C 原生),输出必须一字不差——每版都用差分模糊测试(随机生成程序对跑)验证 |
| 覆盖率 | 95.0% 行 / 90.3% 函数 |
| 自举工具 | 14 个工具是**用 Ming 自己写的**(写文件补丁、目录树、JSON 查询……),工具即语言验证 |

## 最近做成了什么(挑重点)

- **窄类型归一(v0.85–v0.89)**:小整数(比如 `i8`、`u16`)在注解、容器、闭包、枚举里再也不会"悄悄绕回去",越界一律报 M4002。
- **流式读文件(v0.86)**:`read_bytes_range` 可以只读文件的一段,8MB 一块,机器人同学提的"深度帧太大"场景有了起点。
- **只读切片(v0.87)**:`Slice[u8]` 零拷贝查看一段字节,不能越界逃逸(M3051)。
- **防注入标注(v0.61–v0.82)**:来自命令行、环境变量、文件、网络的内容会被标成"不可信"(`Untrusted`),拿去当路径、拼命令、进 eval 会被类型系统拦下,必须显式净化。
- **内联汇编(v0.74)**:要贴机器指令可以,但必须显式声明 `with asm`,而且只有 C 原生后端真正执行,其他引擎明确报错不假装。

## 接下来打算做什么

- **先做一件"证明题"**:用 12–16 个真实小任务,让 Ming / TypeScript / Python 各写一遍,记录"一次通过率、缺陷数、修几轮、花多少 token"——结论不支持也照实发布。
- **然后冻结语言**:不再加新语法,先把引擎之间的遗留分歧清完(v0.90),写清"1.0 承诺什么、不承诺什么",按清单冲 1.0-rc。
- **同时做几个真场景**:日志取证、协议解析、内网小服务、文件完整性——3–5 个,由"没参与开发的人/agent 只看文档"验收。
- **工程收口**:测试套件加超时(这次评估就遇到挂起)、支持矩阵、文档数字自动校验——v0.91 完成。
- **性能与分发**:和 Node/Python/C 同台测一遍并如实公布;让 C 后端至少能编译 hello 级程序;评估单二进制分发。
- **编译器级优化(T6)**:先把"生成出来的程序"变快——先加统计和开关(优化开/关输出必须一字不差),再做常量折叠、死代码清理、拷贝消除、方法调用缓存;自举编译器要等 1.0-rc 和这些数据齐了才谈。
- 原来排着的编辑器补全、Option/Result 窄类型归一 → **冻结期后再做**。

完整的计划和"为什么先做这个",都写在 [docs/plan.md](docs/plan.md) 里。

## 设计上坚持的六句话

1. 明确比简洁重要——写出来的就是全部含义。
2. 安全是默认,不是选项——危险操作要么被检查,要么当场报错,绝不悄悄发生。
3. 副作用必须看得见——没标 `io` 的函数不可能打印,编译器保证。
4. 确定性——同样的代码永远同样的行为。
5. 为"生成 → 检查 → 修正"的循环优化——这正是 AI 写代码的方式。
6. 一种写法——`ming fmt` 就是唯一风格。
