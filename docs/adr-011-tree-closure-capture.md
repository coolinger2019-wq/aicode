## 1. 背景、问题与证据

### 1.1 值语义合同与两引擎实现现状(全链路已逐点核实)

合同(design.md §2.3):"赋值、传参、返回、闭包捕获、集合元素存入——**全部深拷贝**;程序里不存在两个名字共享同一可变结构"。GUIDE §6(函数与闭包):"闭包捕获是值拷贝(创建时快照),之后与外部变量脱钩"。GUIDE 修订记录(v0.4.0 条目):"值语义在 VM 中逐点保真……**闭包捕获 = 创建时快照**"。

**VM 侧(v0.97 后为文档正确面)**:闭包值是扁平 `vclose { fnIdx, captures }`——无 env 链。创建时 `OP.CLOSURE`(`src/vm.js:755-760`)按**编译期捕获计划**(池条目 `{__tag:'plan', v: plan}`,由 `src/compiler.js:1476-1532 compileLambda` 经 `collectFreeNames` 生成)只对被引用自由变量逐槽 `deepCopy`;复制时 `deepCopy(vclose)`(`src/interp.js:141-146`,**v0.97 #81 修复**)对 `captures` 逐项 `deepCopy`。两点的成本都是 **O(自由变量数 × 嵌套内容)**,与定义处作用域里"还有哪些无关变量"无关。闭包帧的 parent 就是 captures 数组本身——**扁平性是 VM 天然 O(free) 的结构原因**。

**tree 侧(缺陷所在)**:闭包值 `{ t:'closure', params, body, env:{vars, parent, mod, localFns, tys}, ... }` 带**深度保持的 env 链**。链的两条生产/消费路径不一致:

| 路径 | 实现点(v0.97.0) | 行为 |
|---|---|---|
| 创建(lambda 求值) | `src/interp.js:1609` → `snapshotEnv`(`src/interp.js:4349-4360`) | **全链递归深拷**:每一帧的全部 vars(含 body 未引用的)+ localFns 浅拷 + tys 全拷 + parent 递归 |
| 复制(let/传参/返回/容器存入) | `src/interp.js:111-130 deepCopy case 'closure'` | vars 逐个深拷;**`parent` 浅拷共享**(`src/interp.js:129`,v0.97 B1 回退后注释如实登记);localFns/tys 保留;mod 共享引用 |

也就是说:**tree 的创建语义(全链快照)与复制语义(parent 共享)自相矛盾**——同一个闭包值,创建时与定义处完全脱钩,复制一次之后却在外层帧上重新挂回共享根。

**env 链的写路径**(复制共享为什么可观察):`assignTo` Ident(`src/interp.js:1276-1284`)→ `lookupVar`(`src/interp.js:1247-1255`,沿 parent 链最近绑定胜)→ **`found.owner.vars.set(...)` 原地写 owner 帧**。两个闭包值的链若共享 owner 帧,一方写、另一方可见——这就是分歧通道。捕获容器的深变异(`v.push` 等)不经 `assignTo`,直接改共享容器对象,通道更宽(§3.3 用到)。

**消费者盘点**(改动面核对,本次全量 grep):interp.js 中 `.parent` 仅 4 处——deepCopy closure(129)、lookupVar(1252)、declaredNarrowTy(1264)、snapshotEnv(4357)。`deepCopy(closure)` 的其它消费者(normBindValue/容器递归/wire)按值形态分派,不触链内部。**tree 侧 wire 无闭包形态**:`syncSpawn`/`syncSpawnAll`(`src/interp.js:2660-2695` 起)对闭包具名拒绝(M4001"spawn 目标必须是模块级命名函数,不能是闭包"),wire 函数族(`vToWire/wireToV`)无 closure 分支——**C1 零 wire 面**。

### 1.3 v0.97 修法为何错误:2^n 的精确数学

**回退修法**(已回退,代码不在 HEAD;plan.md 登记 + `.zcode/review-v097b/oomcheck/oom.log` 崩溃实录):把 `deepCopy` closure 的 `parent` 改为递归 `snapshotEnv(env.parent)`——即"复制闭包 = 递归快照整条 parent 链"。

**指数的机制**(关键:不是"递归"本身,是**双路重复复制**):

- 路径 A:复制闭包 C 时,vars 逐个 deepCopy——vars 里若有**闭包值**(嵌套 lambda 作值),对它递归 deepCopy → 触发它自己的 parent 链快照;
- 路径 B:同一操作里 `snapshotEnv(C.env.parent)` 又把整条 parent 链重走一遍——链上帧的 vars 里**同样的闭包值再被 deepCopy 一次**;
- 每深一层,两条路径各自完整复制剩余链 → `T(d) = 2·T(d−1) + O(1) ≈ 3·2^d`。

对 `p_chain_22`(`.zcode/review-v097/probes/p_chain_22.ming`:22 层嵌套块,每层 `let a_i = (x) => a_{i−1}(x) + 1`,末尾 `let g = f` 一次复制)的结构做模型推演(每层闭包的 env.vars 为空、自由变量全在 parent 帧——该形态下双路重复最大化;模型脚本 `.zcode/adr011/model2n.mjs`,**结构模型非 HEAD 实测;且脚本 C1 腿为单链 O(d) 实现,与正文 (d+1)(d+2)/2 表不同源——实现期对数以正文为准,勿拿脚本 C1 腿对数(v0.97 审查 m1)**):

| d | 回退修法复制操作数(模型) | 对照 2^d | C1 过滤复制(单次复制,帧访问数 = (d+1)(d+2)/2) |
|---|---|---|---|
| 10 | 3,071 | 1,024 | 66 |
| 14 | 49,151 | 16,384 | 120 |
| 18 | 786,431 | 262,144 | 190 |
| 22 | **12,582,911**(≈3·2^22) | 4,194,304 | **276**(帧访问 + 帧构建 ≈×2) |

**实录**:22 层合法程序 OOM exit 134(plan.md 登记口径 4GB;`review-v097b/oomcheck/oom.log` 为默认堆上限(~512MB)下 `Reached heap limit` 的崩溃实录,两者同根);`p_bind_closure_hot`(1M 次 `let g = f`,f 链短)tree +55%。审查 B1 否决,回退,#82 登记开放 P1。

**两个必须写清的推论**:

1. **memo 化(帧/值身份表)能消指数**——同一闭包值在一次复制内只处理一次,O(可达结构) 一遍、内部共享保留。但它**不消渐进**:复制成本仍是 O(整条可达链的内容),与自由变量数无关。
2. **为什么选 C1 而不是"修补回退修法(memo 化)"**:`p_big_parent`(`review-v097/probes/p_big_parent.ming`:闭包 `() => 1`(**零自由变量**)定义在持有 10000 元素 Vec 的作用域里,循环复制 2000 次)是判别锚——现状 tree deepCopy **36,009**,其中**缺陷可归因部分 = 创建时 snapshotEnv 对 big 的 10,001 条目快照**(分解实测:t7 创建-only 探针 30,009,其中 big 快照 10,001、其余为循环路径的 int 恒等计数;见附录 A);VM deepCopy **4,005**(计划捕获为空,big 全程不进闭包;VM 计数低另有口径原因——m1 恒等快路径连计数都不进,不可当 tree 的计数平价目标)。memo 化的回退修法:每次复制全链可达结构 = 2000 × 10,001 ≈ 2,000 万条目——比现状慢且方向错;C1:创建 O(free)=O(1)、复制 O(1)/次——**big 全程不被任何闭包拷贝**(计数面 −10,001)。**语义目标(§2)直接淘汰"拷无关变量"的一切方案。**

### 1.4 对照小结

| | VM(vclose) | tree(closure)现状 | 语义目标 |
|---|---|---|---|
| 创建 | 按计划 O(free) | 全链 O(可见环境) | 按自由变量(行为不变,成本降) |
| 复制 | captures 逐项 O(free)(#81) | vars 拷 + **parent 共享**(缺陷) | 自由变量过滤快照(修复) |
| 块结构可观察? | 否(两 wrapper 同值) | **是**(n3:1/1/2 vs 1/2/3) | 否 |

## 2. 语义目标(先定语义再定实现)

### 2.1 单句陈述

> **闭包值的复制 = 对"其 body 求值时可经 env 链按名到达的绑定状态"做值快照;body 未引用的绑定不可经该闭包观察,复制与否、是否共享,均不可观察。**

论证骨架与 ADR-010 §2.2(身份不可观察性审计)同构:闭包值的一切语言可观察面 = 调用它(body 求值)。body 求值只能经 `lookupVar`/`declaredNarrowTy` 按**名**触达 env 链(§1.1 写路径盘点);一个名字若不出现在 body 的任何 Ident 位(collectFreeNames 的自由变量集),它就不可达,其值是否被拷贝、拷贝前后是否共享,在一切可观察通道(stdout/exit/panic 首行/`==`/`debug`/Map 键/配额)上不可区分。因此**"只快照自由变量"与"全链快照"语义等价**,而前者成本 O(自由变量 × 内容)。

**配额面注意**(与 ADR-010 §5.2 同口径):`deepCopy` 不计费(`--max-alloc` 不受影响);`MING_STATS.deepCopy` 是观测量,会**下降**(创建点不再拷无关变量)——同版本基线纪律,跨版本比较无意义。

### 2.2 六条可测命题(验收的语义面,全部可写成锚程序)

- **P1 复制隔离**:任意复制边界(let/实参/返回/Vec/Map/struct 字段)后,两个闭包值互写不可见——含捕获**容器**的深变异(A 闭包 `push`,B 闭包读不到)与计数器(`c = c+1`)。
- **P2 创建快照**:创建后与定义处脱钩(既有语义,不变)——定义处后续写 `c`,闭包内读不到。
- **P3 块结构不可观察**:n3 的 wrapA ≡ wrapB(同为 1/1/2)。
- **P4 同值持久**:同一闭包值跨多次调用,捕获变量的写**累积**(计数器语义;这是 C2 被否决的依据)。
- **P5 元数据生存**:tys(窄型归一,t1 锚:`6/6/7/5`)、localFns(t4 锚:`7/7`)、`__retSpec`/narrowParamTypes/narrowRetSpec/e79 全部跨复制保留。
- **P6 遮蔽正确**:自由变量的 owner 解析 = lookupVar 同口径(最近绑定层胜);复制后链上遮蔽关系不变(深度保持)。

### 2.3 C1 的运行期快照集合 vs VM 的编译期捕获计划——差异写透

**集合的选择**:两者对 checker-合法程序选出**同一个名字集合**——都从同一 body AST 出发。**实际语义 = 纯过近似**:自由集 = body 全部 Ident 引用 − 形参 − `FnStmt` 子树(`compiler.js:1547-1555`);**内层 let/for/while-let/match 绑定名不排除**——collectLambdaLocals 对真实 lambda 体是死代码(BlockExpr 的语句在 `node.block.stmts`,其 case 读 `node.stmts` 从不下钻,从未向 bound 添加过名字,v0.97 审查 M1 实证),且**该死代码目前是承重的**:内层 `let g = g+1` 的 init 引用外层 g 被收进自由集,恰是 rv1/rv7 双引擎正确语义的来源——P0 严禁"顺手修复"该函数(修则 rv1/rv7 翻转,见 §3.1.2 锚钉)。差异在**三点**,全部要写进实现合同:

1. **坐标不同**:VM plan 把自由名解析为**外层函数帧的槽坐标**(`{local: slot}` / `{cap: idx}`,`compiler.js:1493-1504`),编译期定死;C1 在**运行期按名沿链解析 owner**(lookupVar 口径)。对合法程序两者命中同一绑定;运行期解析天然免疫"槽位重排",但**依赖 collectFreeNames 的完备性**——分析漏名 → tree 静默丢绑定,且 VM 腿同样漏(plan 同源)→ **三腿一致地错**,fuzz 抓不到语义错只能靠定向锚(§7 诚实边界 #3,§5 变异实验)。
2. **localfn 名单**:VM 对解析为本地函数的自由名**不捕获**(`r.kind === 'fn'` → fnBinds,`compiler.js:1496`;体编译为直接 LDFN);tree 的名字解析走 `env.localFns`(`lookupVar:1251`),**C1 必须把 localfn 命中的条目带进快照**(localFns 浅拷,现状 deepCopy 同口径)——即 C1 集合 = VM plan 集合 ∪ {解析为 localfn 的名字}。t4 锚锁定。
3. **过近似(over-approximation)对齐**:`collectFreeNames` 对**最外层 body 不做 let 预绑定**(`compileLambda` 只把 params 给 `bound`,`compiler.js:1478`;`collectLambdaLocals` 只用于**内层** lambda)——body 自己 `let g = ...` 遮蔽外层 g 时,g 仍被收进自由集。VM 侧后果:多捕获一个用不到的槽(不可观察,仅成本);C1 侧后果:多拷一个用不到的绑定(同样不可观察)。**C1 不做"更精"的分析**——保持与 VM 同一过近似,才是"同一分析、两个消费者"的单一事实来源;更精的分析留给 O2e(ADR-010 §4.4.5)那类优化批次。

**创建时点的语义差异**:无。VM 捕获值拷贝发生在 CLOSURE 指令执行时,tree 快照发生在 lambda 求值时——同一时刻、同一"创建时快照"语义(P2)。

### 2.4 明确不改变的面

- **创建时点语义**(快照)不变;捕获变量的写**不穿透回定义处**(现状已如此——snapshotEnv 已脱钩,C1 保持)。
- **捕获 mut 判定**不变( checker 层 M3004 面;运行时无关)。
- **VM 侧零改动**(vclose/plan/CLOSURE/#81 全部原样);wasm/C 后端零改动(两者从 AST 编译,tree env 是解释器内部结构)。
- **wire/分布式零改动**(§1.1:tree 无闭包 wire 形态)。
- **panic/配额/strict-wasm 面零改动**(C1 不触 M 码、不触字节码)。

## 3. 设计候选

### 3.1 C1:自由变量捕获计划下沉树引擎(**主选,建议采用**)

#### 3.1.1 机制:一个函数,两个调用点

新增单一函数(建议名 `captureEnvFor(body, params, chain) -> env`,放在 `src/interp.js` snapshotEnv 旁):

1. **自由变量集**:`free = collectFreeNames(body, params)`——分析本体 O(body AST),**结果缓存在 Lambda AST 节点上**(如 `body.__freeNames`,懒计算;AST 节点随 parse 生成、生命周期单次编译,无失效问题;checker/compiler 已有向 AST 回写字段的先例——`e.narrowRetSpec` 等,`compiler.js:1528`)。创建与复制共用同一缓存。
2. **owner 解析**:对每个 free 名,沿 chain 从内向外找最近绑定层(lookupVar 同款遍历;命中 vars → 记 (帧, 名);命中 localFns → 记 (帧, localfn);全链未命中(模块项/内建)→ 丢弃)。单遍 O(free × 链深)。
3. **深度保持过滤重建**:为链上**每一帧**建新帧(空壳也保留——P6 遮蔽关系靠帧序不变性,且链深即块深,塌缩空帧的微优化登记不做,v1 保深度最易证明):新帧 vars = 深拷该帧被认领的绑定;新帧 tys = 相应 tys 子集(t1);新帧 localFns = localfn 命中条目浅拷(t4);parent 逐层挂接;`mod` 共享引用。每帧 localFns 的非命中条目**不拷**。

**两个调用点**:

- **创建**(`src/interp.js:1609`):`V.closure(e.params, e.body, captureEnvFor(e.body, e.params, env), ...)` 替换 `snapshotEnv(env)`。运行期执行中的链被过滤快照——body 未引用的绑定(big)不进闭包。
- **复制**(`src/interp.js:129 deepCopy case 'closure'`):vars 整表拷改为 `captureEnvFor(v.body, v.params, v.env)`。**复制中遇到的嵌套闭包值**(某自由变量的值本身是 closure)递归走同一函数 → 每个绑定值沿"自由变量边"恰复制一次,**无双路重走**(§1.3 的路径 A/B 合一)。p_chain_22 形态复制成本从模型 12.6M → 单次复制 ≈276 次帧访问(×2 计帧构建,§1.3 表;实测待 P2 落地复核,门槛见 §5 G2)。

旧 `snapshotEnv` 删除或保留为死代码由实现者定——建议删除(全仓唯一调用点就是 1609;保留会留下"两条快照路径"的漂移温床)。

#### 3.1.2 边界逐条(任务指定四面)

| 边界 | 处理 | 依据/锚 |
|---|---|---|
| **let 声明 vs 引用** | body 内层(嵌套 lambda 之外)的 let/for/while-let/match 绑定名:collectFreeNames **不排除**(外层 body 无 collectLambdaLocals 预绑定)→ 过近似收进 free → owner 解析命中则多拷(不可观察)、未命中则丢弃。内层 lambda 的绑定名**不排除**(纯过近似——collectLambdaLocals 为无效路径,承重勿修:rv1/rv7 锚钉;修复会翻转 init 引用外层名的双引擎正确行为) | §2.3 差异 3;VM 同型 |
| **遮蔽** | owner 解析 = 链上最近绑定层胜(lookupVar 逐字口径);深度保持重建保证复制后遮蔽结构逐帧不变 | P6;n3 wrapB 的 g 在 parent 帧 |
| **mut 判定** | 运行时不判定 mut——赋值合法性是 checker 静态面(M3004);运行时只管"哪个帧 owner" | §2.4 |
| **分析成本** | O(body AST) 每 lambda 位**一次**(AST 节点缓存);owner 解析 O(free × 链深) 每次创建/复制;深链形态 p_chain_22 创建合计低阶多项式(推演 ≈1,800 次访问,d=22;与现状 435 条目同数量级)、复制单次 ≈552 次访问/构建(§3.1.5) | §1.3 模型;G2 门槛 |

**localFns 深层的诚实登记(审计项 A-LF,不在本修复面)**:localFns 条目 `{name, decl, mod, env: 定义块 env}` 浅拷后 **entry.env 仍指向原定义块 env**(现状 deepCopy 亦然)。该共享是否可观察取决于"本地 fn 能否经链触达定义块的可变值"——checker M3001(v0.59 #44:**本地 fn 不捕获外层局部**)使值面不可达;entry.env 仅剩名字解析(localFns 递归/兄弟)与 mod 用途。本 ADR **不改变**这一现状(浅拷口径逐字保留),登记白盒探针建议(两份复制各经 localfn 调用,断言无共享可观察面),若未来放宽 M3001 必须重开此项。

#### 3.1.3 正确性论证

- **与全链快照等价**(P1–P6):可达绑定逐名深拷 ⇒ 任何 body 求值路径逐名命中同值;不可达绑定两侧都不可观察(§2.1)。
- **与 VM 逐字**(三腿):自由名集合同源(§2.3 差异 1/3 对合法程序无行为差);localfn 差异(差异 2)是 tree 名字解析的既有事实(现状 snapshotEnv 也带 localFns),非新分歧。
- **无指数**:单遍过滤重建,绑定值沿自由变量边各拷一次;同一值被两个自由名引用(`f(v, v)` 式双名)会拷两份——**正确**(两名字本就该是两个私有值:值语义下 `let b = a` 已拷)且非指数(节点数 × 引用数,非 2^重走)。一次复制内的内部共享保留(memo)登记为可选精化,v1 不做。

### 3.2 C2:持久化 env / COW(**否决——语义错误,两层论证**)

**形态**:env 节点不可变;写入时沿路径拷贝(path-copy),旧结构共享——design.md §2.3 提到的路线图"v0.3+ 用写时复制(COW)消除常读路径的拷贝开销"的泛化版。

**否决论证 1(致命:变异丢失)**:Ming 的闭包捕获是**按值快照**(GUIDE §6),捕获变量的写要落在**闭包值自己的链**上并跨调用持久(P4——`a = (x)=>{c=c+1;...}` 连续调用累积,实测 t1/e79 皆然)。纯持久化下,写路径拷贝产生的新链挂在**调用帧 fenv**(`callClosure:1055` 每次调用新建)之下,调用返回即整体丢弃——**计数器归零**。要不丢,必须把新链**写回闭包值本身**——闭包值此刻在栈/槽里,"写回值" = 值可变 = 破坏值语义本身。死路。

**否决论证 2(方向相反)**:函数式语言(persistent map/HAMT)的成熟方案解决的是"**同一可变结构被多名字共享**时的写隔离"——前提恰恰是存在共享可变结构。Ming 的合同禁止共享可变结构(§2.3),tree 的问题不是"共享了要隔离",而是"**复制得不够深**"。Persistent env 在 Ming 语境里唯一能成立的形态是"把帧变成 COW 值、共享时才真拷"——那就是 C3(§3.3),它自己有更深的问题。**C2 v1 否决;COW 运行时维持 design.md 的长期方向登记,不预支**(与 ADR-010 §8 "COW/引用计数运行时:不做"同口径)。

### 3.3 C3:惰性 copy-on-share + 代际标记(**备选,不推荐**)

**形态**(v0.97 修法的改良):env 帧加所有权/代际标记;`deepCopy(closure)` **不拷**,只把可达帧标记 shared(代际 bump);写路径(`assignTo` Ident → `found.owner`)遇 shared 帧先拷帧(必要时级联拷中间帧重链 parent)再写。

**正确性洞 1(致命:容器深变异)**:`v.push(9)` / `m[k]=` / `s.f=` 不走 `assignTo` 帧写——直接改**共享容器对象**(§1.1 写路径盘点)。帧级 COW 完全挡不住:两个闭包值的链共享同一个 Vec 对象,push 互见 → 违反 P1。要堵住只能在**读**捕获容器时做私有拷贝——而"读"无法预知后续是否将写(无别名分析),逐读 deepCopy 比全量拷贝更贵,"首次读拷贝"又会把未写副本也翻倍。结论:要保 P1,C3 必须在**共享标记时**就深拷全部容器值 = O(可达全结构)/次——回到 memo 化回退修法的性能面。

**正确性洞 2(语义边界复杂)**:privatize owner 帧需重链中间帧,中间帧可能 shared → 级联判定;"谁触发复制"只有写点可判,读点不判 → **两个只读副本长期共享**(合法)与"一个读一个写"(须隔离)的边界完全压在写点,而容器变异绕开写点——两洞叠加,标记传播规则无法局部化。

**登记价值**:若 C1 的 collectFreeNames 出现**遗漏面**(某可达绑定未进快照 → tree 静默读丢),C3 的"保守全保 + 写时分离"不依赖分析完备性,可作为**回退方案**——正确性可救(memo 化后非指数),性能次优(p_big_parent 门禁过不了)。**裁决建议:不采用为主案;登记为 C1 的风险对冲**。

### 3.4 C1-alt 变体登记:扁平化 tree env(vclose 化)(**否决:改造面与语义收益不成比**)

把 tree 闭包也改成扁平 captures(创建时按 plan 装数组,运行期查表)——两引擎表示统一。否决理由:tree 的 env 链同时服务**非闭包执行**(childEnv/execBlock/lookupVar/assignTo/declaredNarrowTy/contract env/localFns 提升),扁平化等于重写 tree 作用域模型全部写路径;语义目标(§2)只要求**行为一致**,不要求**表示统一**;VM 侧对 tree 值无任何消费(two-engine 值仅在边界互传,按值形态分派)。规模预估 >500 行 vs C1 ≈150 行,收益为零。登记不做。

## 7. 诚实边界

1. **本 ADR 未实施**——全部"C1 后"数值是推演/模型(§1.3 模型表为结构模型,非 HEAD 实测;HEAD 无该代码);§5.4 门槛数字以待实现实测复核为准,超门即回设计。
2. **C1 的正确性地基 = collectFreeNames 完备性**——它今天由 VM 腿背书(三引擎差分),但分析遗漏时**三腿一致地错**(plan 同源),fuzz 对语义错失明;防线 = §5.5 定向形态 + 变异实验 + 新语法一律过 freenames.js 单点(注释合同)。
3. **C1 与 VM plan 的三点语义差异**(坐标/localfn 名单/过近似)已写透(§2.3)——实现者不得"顺手"精化任何一点,同源过近似是特性不是缺陷。
4. **GUIDE §6 现行措辞与实测矛盾**:"捕获的变量不可在闭包内赋值"——实测(t1、n1 语料)闭包内对捕获 mut 变量赋值**合法且作用于闭包私有副本**(6/6/7/5 双引擎一致)。该句应校准为"闭包内可赋值捕获的 mut 变量,写落在闭包自己的快照上,与外部变量脱钩"。P3 修,零语义。
5. **A-LF 审计项**:localFns 条目 `env` 共享在 M3001 下论证不可观察,但这是**论证**不是证明;白盒探针登记(§3.1.2),放宽 M3001 时重开。
6. **p_chain_22 复制成本是 O(d²) 不是 O(d)**(每闭包复制走自身链后缀;单次复制推演 ≈552 次帧访问/构建,§1.3 表);与 VM 的 O(d) 有常数差,门槛按墙钟定(§5.4),不追求与 VM 计数对齐。
7. **一次复制内的内部共享**(同一值被两个自由名引用)v1 拷两份——正确、非指数、有常数;memo 精化登记不预支。
8. **计数口径**:tree 创建点拷贝量下降是**观测量变化**(同 O1/#81 先例);opt-baseline 的历史 deepCopy 列在闭包程序上会漂移——重生成时如实更新(H 验 §5.1 同款提醒)。
9. **并行批次边界**:本 ADR 独占 `docs/adr-011-tree-closure-capture.md`;experiment-design 文档(并行 Agent)不引用本文为依据,交叉点只有 §8 的 ADR-010 关系。
