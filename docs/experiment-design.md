## 1. 目的与假设

**目的**:把 Ming 北星核心论点——"AI 用 Ming 更少写错"——从主张变成可复核数据。
在**同模型、同提示骨架、同验收标准**下,对比 Ming 与两个主流对照语言在
14 个固定工程任务上的生成质量与修复成本。

**假设(预注册,采集后不得增删)**:

- **H1(首次通过率)**:同一任务集上,Ming 的首次通过率(M1)高于 TypeScript 与
  Python 两个对照,且相对差 > 20%。
- **H2(修复轮次)**:同一任务集上,Ming 的平均修复轮次(M3)低于两个对照,
  且相对差 > 20%。

次要观测指标 M2/M4/M5(缺陷数、token、墙钟)按同判据报告,但不构成假设的
支持/不支持判定主依据(登记为辅助证据)。

## 2. 任务集(14 个 × 三类)

任务语料入库于 `tests/experiment/tasks/<id>/`,每任务含:`spec.md`(人话规格)、
`prompt.md`(固定提示模板)、`input/` 与 `expected/`(输入与期望输出 fixture)、
`verify.ming`/`verify.js`/`verify.py`(三语言黑盒验收)、`solutions/`(参考实现)、
(仅 B3/B4)`mock_server.mjs`/`harness.mjs`(服务生命周期 harness,单一 Node 实现,
三语言 verify 共用——见 §5.3)。

| id | 类 | 名称 | 规格要点 | 程序调用形状(三语言一致) |
|----|----|------|----------|--------------------------|
| a1_log_clean | A | 日志清洗 | 行判定(级别字段)+字段提取(user/action)+过滤 DEBUG+四级别汇总行 | `prog <input.log>` |
| a2_batch_rename | A | 批量改名 | 字典序处理;补零改名/入子目录/冲突跳过三类规则;stdout 计划 + 输出目录落盘 | `prog <input_dir> <output_dir>` |
| a3_csv_to_json | A | CSV→JSON | 固定方言(无引号);4 列;坏行(字段数≠4)Err 化为 errors 数组;紧凑 JSON 单行输出 | `prog <input.csv>` |
| a4_dedup_stats | A | 去重统计 | 分块文件依次处理;total/unique/repeated + Top-3(次数降序,并列行名升序) | `prog <chunks_dir>` |
| a5_word_topk | A | 词频 Top-K | 空白切词;计数;Top-5(次数降序,并列词升序) | `prog <words.txt>` |
| b1_json_deep_merge | B | JSON 深合并 | 对象∩对象递归,否则 B 胜;键序 = A 序 + B 独有追加;紧凑单行 | `prog <a.json> <b.json>` |
| b2_validate_pipeline | B | 数据校验管线 | 4 字段手写 schema 校验(不短路);逐记录错误行 + ok/failed 汇总 | `prog <records.json>` |
| b3_fetch_aggregate | B | HTTP GET 汇总 | 3 个本地模拟源 + 1 个 404;按参数序拉取解析;逐源行 + summary;不依赖外网 | `prog <url1..url4>` |
| b4_serve_handler | B | serve handler | 请求→响应映射(固定响应体);请求矩阵 6 条;响应 transcript 逐字比对 | `prog <port>`(长驻服务) |
| b5_json_path_query | B | 嵌套 JSON 路径查询 | 点路径逐段下钻(数字段=下标);MISSING 语义;值渲染规则固定 | `prog <doc.json> <queries.txt>` |
| c1_spawn_map | C | spawn 并行汇总 | 4 分片平方和(spawn/线程并行);父按序合并 | `prog`(无参) |
| c2_timeout_fallback | C | 超时与降级 | 慢子任务(400ms)100ms 超时→默认值;快子任务(50ms)取真值 | `prog`(无参) |
| c3_budget_degrade | C | 资源配额降级 | 程序内预算规则(逐记录累计成本超预算→停在越界记录前);跨语言以行为规则为准 | `prog`(无参) |
| c4_sharded_counter | C | 竞态防护 | 分片计数(公式生成数据)+父任务合并;禁止共享可变计数器裸累加 | `prog`(无参) |

**任务构造原则(登记)**:

1. **输入对被测程序不可预知**:A 类与 B1/B2/B5 的真实数据只存于 `input/` fixture,
   `prompt.md` 仅给格式说明与**构造用示例**(示例内容 ≠ fixture 内容)——防止
   "背答案"式硬编码;B3 数据在模拟源后端;C 类数据由规格内公式定义。
2. **确定性**:全部输入/输出固定;不依赖时间/随机/哈希序;输出格式逐字固定
   (分隔符、键序、空格数均为规格的一部分)。
3. **错误行为进规格**:每任务至少一个错误路径(坏行/缺字段/404/超时/配额越界/
   冲突),验收覆盖正负两路径。**验收粒度 = fixture 可观测行为一致,非全规格覆盖**(边界语义不逐条触达——T1.3 不得过度解读,详见 §8 缺口 8)。
4. **跨语言语义等价**:验收按"行为规则"而非语言机制写(例:C3 的 Ming 侧原生
   `--max-alloc` 不是验收对象;三语言实现同一程序内预算规则)。B3/B4 的模拟源
   与请求矩阵为单一实现(harness),三语言仅客户端/服务端程序不同。
5. **防作弊**:程序禁止读取任务 `expected/` 与 `solutions/` 目录(诚信规则,
   执行者代码审查标记;验收器不做机械检测——如实登记为局限)。

## 3. 指标定义与判据(预注册)

| # | 指标 | 定义 | 采集方式 |
|---|------|------|----------|
| M1 | 首次通过率 | 首次生成即通过验收的 run 占比;每语言 42 run(14 任务 × 3) | 首轮 verify 退出码 |
| M2 | 缺陷数 | 每 run 的(静态检查错误条数 + 验收失败项数)合计,按任务归一(任务内 3 run 平均) | 静态检查输出 + verify 输出 |
| M3 | 修复轮次 | 从首次生成到首次通过验收的修复循环数;封顶 5(5 轮仍未过记 5 并标 `failed`) | 执行日志 |
| M4 | token 消耗 | 单任务全程(生成 + 全部修复轮)prompt+completion token 合计 | 执行环境计数;无精确计数时以字符数/4 估算并标注 |
| M5 | 墙钟 | run 开始至验收通过或轮数耗尽的分钟数 | 执行环境计时 |

**判据**:

- **显著**:两语言在同一指标上的**相对差 > 20%**。相对差定义(预注册):
  两值均 > 0 时 = `|a−b| / min(a,b)`;任一值为 0 时只记绝对差并标"不确定"
  (分母为零的相对差不定义)。
- **不做 p 值宣称**:样本量(每格 3 run)不支持显著性检验;报告中不出现
  "显著/显著水平"等统计学术语,只报相对差与三态结论。
- **样本不足条款**:任一指标两值相对差 ≤ 20%,或任务级结果方向不一致
  (部分任务支持、部分反向),该指标结论记"不确定"。
- **结论三态**(对 H1/H2 各自独立判定):**支持**(Ming 相对差 > 20% 优于两个
  对照且方向一致)/ **不支持**(Ming 劣于任一对照 > 20%) / **不确定**(其余)。
  "不支持"结论必须发布,不得隐去。

## 5. 执行流程(T1.2 规程)

### 5.1 单次 run(任务 × 语言 × 重复序号)

1. 读取该任务 `prompt.md`(含对应语言约束节)作为唯一输入发给模型。
2. 保存生成物为 `work/<run_id>/solution.<ext>`;记录首轮 token/墙钟。
3. 静态检查:Ming `ming check --json`(错误数入 M2);TS `tsc --noEmit --strict`;
   Python `python -m py_compile`。静态检查**不是**通过门槛,错误计数入 M2,
   但运行时能过验收仍算通过(与人类实践一致——按语言惯例,Ming/TS 先查后跑)。
4. 验收:`node tests/experiment/tasks/<id>/verify.js [prog]` /
   `python .../verify.py [prog]` / `node bin/ming.js run .../verify.ming -- [prog]`
   (缺省被测程序 = `solutions/solution.<ext>`;全部命令**从仓库根目录**运行)。
5. 通过 → 记录 M1=通过、M3=当前轮数、M4/M5,结束。
6. 未通过 → 将静态检查与 verify 输出**原文**回传模型修复(步骤 2 重复),
   轮数 +1;封顶 5 轮。
7. 写一行 JSONL 到 `tests/experiment/results/results.jsonl`:
   `{run_id, env:{os,node,python,ming_head,tsc}, task, language, repeat, model, temperature, rounds, first_pass,
   defects:[...], tokens:{prompt,completion}, wall_ms, verdict, ts}`。
8. 保存该 run 全部对话原文(缺陷分析证据)。

### 5.2 重复与汇总

- 每任务 × 语言 × **3 次**;重复间仅随机种子/采样不同,任务与提示不变。
- 汇总表按 §3 指标聚合;任务级与语言级两级报告;原始 JSONL 与对话原文一并入库。

### 5.3 服务型任务(B3/B4)的 harness

- B3 `mock_server.mjs` / B4 `harness.mjs` 为**任务自带**的固定 harness(单一
  Node 实现):负责模拟源/服务生命周期(启动、就绪探测、固定请求矩阵、关停)。
- 三语言 verify 各自实现"调 harness → 断言输出/退出码"的验收逻辑;harness
  打印的 transcript 与被测程序 stdout 为唯一断言对象,其格式在 spec 中逐字固定。
- Ming 侧动机如实登记:Ming 程序无外部进程 kill 能力,B4 长驻服务只能由
  harness(Node)启动与关停——这是 harness 单一实现的直接原因。

### 5.4 作者-执行者分离声明

- **本设计(A5b)不执行实验**。执行(T1.2)由独立 agent/会话承担;执行者不得
  修改 `tasks/**`、本文件判据与指标;发现语料缺陷 → 登记到 `docs/gap-log.md`
  并停止相关格采集,不得就地修改后继续。
- 执行 agent 的上下文隔离:每 run 只喂 `prompt.md`,不提供仓库访问、不提供
  本文件与 spec(避免"验收标准泄漏进提示");执行者本人只按规程操作。

## 6. 局限(禁止外推)

1. **单机单环境**:win32 + Node 24.11 + Python 3.10.11;结论不跨平台外推。
2. **单模型**:一个模型一个快照;不支撑"所有 AI"的宣称。
3. **小样本**:14 任务 × 3 语言 × 3 重复 = 126 run;任务级格子仅 3 run——
   任务级数字只作线索,不作结论。
4. **任务构造偏差**:任务由 Ming 项目成员(A5b)设计,可能无意识地偏向
   Ming 的能力面(显式类型/效果系统/确定性);三类任务以 CLI/数据/并发为主,
   不覆盖 GUI/数值计算/ML 等场景。
5. **提示语言**:任务描述为中文;模型对中文/英文提示的表现差异未控制。
6. **硬编码作弊面**:固定输入 + 固定验收下,模型理论上可背输出;已通过
   "输入不进提示"(§2 原则 1)压低,但无法机械杜绝——执行者审查标记
   `suspicious`,并入质量备注,不改判通过与否(预注册:审查不影响 M1)。
7. **B3/B4 harness 单实现**:harness 缺陷会同时影响三语言(风险共担);
   harness 本身经参考实现验证(见任务目录 solutions 全绿记录)。
8. **Python 版本偏差**:3.10.11(实况)vs plan 写 3.12——已如实登记,结论
   措辞必须带此偏差。

## 8. 语料有效性验证记录与留给 T1.2 的缺口

**已验证(2026-11-20/21,A5b)**:

- 全部语料 `.ming`(solutions ×14 + verify ×14)通过 `ming fmt --check` 与
  `ming check`。
- **42 个 verify 腿全绿**:14 任务 × {ming, ts, py},对各自 `solutions/solution.*`
  逐字节通过(复跑两次;第一次采集期修正 A1/INFO 计数与 C1/平方和两处 fixture
  手工算术错误——三语言输出一致而 fixture 不符即暴露,恰为"验收有效性"的实证)。
- **验收有效性抽查**:向 verify.js/py/ming 喂入错误语言/错误任务的参考实现,
  全部正确 FAIL(stdout mismatch / 参数错误 / exit 非 0)。
- B3 mock(三端口模拟源 + ready 文件协议)与 B4 harness(服务生命周期)在
  三语言腿下运行通过;端口占用自动漂移路径未在冲突环境实测(登记 §6.7)。

**实测发现(执行者必读的环境地雷,均已在语料内消化)**:

1. **Node 24 Windows:`fetch` 后调用 `process.exit` 会触发 libuv 断言崩**
   (`Assertion failed: !(handle->flags & UV_HANDLE_CLOSING)` → 退出码
   127/0xC0000409)。凡发起过 fetch 的 TS 程序必须 `process.exitCode` +
   自然退出——已写入 B3/B4 prompt 的 TS 约束与 B3 参考实现注释。
2. **长驻服务程序不得在 `listen` 后调用 `process.exit`**(会杀掉刚起的服务);
   B4 的 TS 参考实现已按"错误路径才 exit、正常路径自然长驻"重写。
3. **Ming 长驻服务必须经 `node bin/ming.js run <文件> -- <端口>` 启动**
   (裸 `node file.ming` 不可运行);B4 ming 腿的 harness 命令片段为此带
   `run … --` 中段。harness 的端口追加约定("末参数 = 端口")已写入
   harness 头注释与 spec。
4. Python 子进程输出在 Windows 管道含 `\r\n`:verify.py 一律
   `text=True + encoding="utf-8"` 采集并按 universal newlines 归一,期望文件
   统一 `\n`(三语言腿各验各语言,不跨腿采集,无交叉污染)。

**留给 T1.2 的缺口(执行前必须解决)**:

1. `tsc` 未预装:`npx -p typescript tsc` 需网络下载或预装 TypeScript;
   版本(≥5.x)与安装方式记入环境指纹。
2. 结果采集器 `tests/experiment/run.mjs`(零依赖)未实现——T1.2 交付物
   (plan §4.15.4 T1.2 原文要求);本设计只锁定规程与 schema。
3. 模型访问方式(哪些 API、快照号、温度支持)需维护者确认后回填 §4 表格
   "模型"行;确认前不得开始采集。
4. B3/B4 端口段(21031+/21241+)在执行机上的占用检查步骤需并入 run.mjs
   (预检失败该格记 `env_blocked`,不计入样本);并发跑多格时端口漂移会让
   `env_blocked` 判定复杂化,建议串行执行服务型任务两格。
5. 修复轮的反馈回传格式(静态检查输出 + verify stderr 原文的拼接模板)需在
   run.mjs 中固定,三语言形态一致(设计 §5.1 步骤 6)。
6. (v0.97 审查 m-1)prompt.md 含三个语言约束节——run.mjs 组装时必须裁出
   "正文 + 对应语言节"发送(裁剪规则:按语言节标题定位,禁止整文件发送,
   否则模型看到三语言约束违背控制变量)。
7. (v0.97 审查 m-2)结果 JSONL schema 增 `env:{os,node,python,ming_head,tsc}`
   字段(逐 run 环境指纹;§4 表格口径落地)。
8. (v0.97 审查 m-5/m-6)plan↔本设计的工具面漂移登记:
   Python 侧编译检查用
   `python -m py_compile`(任务无 pytest 套件,plan 原文 pytest 表述以本设计为准);
   Ming 侧暂不记录 fix 处方应用面(预注册指标未含,补录需改指标表)。
