## 1. 问题背景：AI 编程需要“任务通用性”，但不必由单一语言承担



AI 编程要覆盖多样性任务，确实需要通用性。但不精通编程的人要“从程序设计中脱离出去”，依赖的是一条完整闭环：



```text

自然语言意图

  → AI 任务规划

  → 多语言代码生成

  → 自动测试

  → 关键不变量形式化验证

  → 沙箱执行

  → 失败修复

  → 部署

这条闭环中，Ming 不需要占据全部环节，只需要占据最关键的一环：



形式化验证关键不变量，并提供机器可消费的证明与契约。



多样性任务由现有生态实现：



任务类型	实现生态	Ming 的角色

GUI / Web	JS / TS / Python	验证权限、数据流、关键契约

数据分析	Python / SQL	验证敏感数据访问效果与聚合契约

系统工具	Rust / C	验证内存与副作用边界

Agent 工作流	多语言编排代码	作为模块间契约与效果策略执行点

高性能计算	FFI 外部库	声明效果与契约，编排可信边界

因此，Ming 的发展方向不是“功能补齐竞赛”，而是：



做 AI 生成代码的可信验证层、契约层与效果策略执行层。



## 2. 先区分三种“通用性”
通用性类型	含义	是否需要 Ming 承担

用户通用性	不精通编程的人用自然语言完成各种任务	不需要，由 AI 前端承担

任务通用性	GUI、爬虫、数据分析、系统脚本、AI 应用等	不需要单一语言，由多语言生态 + 运行时 + 库承担

语言通用性	一门语言什么都能写	不需要，也不现实

参考事实：



SQL 不通用，但支撑了数据任务；



WebAssembly 不是日常源语言，但成了通用目标；



LLVM IR 不是给人写的，但支撑了无数语言。



Ming 更合适的生态位是：



可验证 IR / 契约层 / 可信核心。



## 3. Ming 如何不变成“孤岛”
### 3.1 定位为“可验证核心”，支持渐进嵌入

不要求用户重写整个程序。允许：



Python / JS / Rust 项目把关键模块编译成 Ming 验证的 WASM/C 组件；



Ming 调用外部库，但通过 ffi 效果和契约约束；



关键模块可信，外围生态通用。



### 3.2 做“双向契约桥”，而不是替代通用语言

从 Python / TS / Rust 的类型和注解中自动提取契约，生成 Ming 验证桩；



Ming 验证后的模块导出为标准 WASM/C ABI，供任何语言调用；



为常见库生成带效果声明的绑定，例如 fs("/data/\*")、net(host="api.example.com")。



这样 Ming 不跟生态竞争，而是给生态加“可信证书”。



### 3.3 对用户透明：Ming 是 AI 的后端，不是人的前端

AI Agent 负责把自然语言转成 Ming 核心逻辑和契约；人类只做意图确认和验收。



Ming 的诊断应同时提供：



机器可读证明报告；



人类可读解释。



不精通编程的人不需要学 Ming，但能看懂“AI 证明了什么、没证明什么”。



### 3.4 从“全程序语言”转向“项目级验证编排”

提供多语言项目级验证：



扫描一个仓库；



识别关键边界；



生成 Ming 契约桩；



验证跨语言调用。



Ming 的价值随项目复杂度增长，而不是要求从零重写。



### 3.5 强化沙箱、效果策略和权限模型

AI 生成代码的多样性任务往往伴随高风险副作用。Ming 的效果系统应参数化：



ming

with fs("/data/\*\*")

with net(host = "api.example.com", scheme = "https")

with exec(allow = \["git", "make"])

这比“通用语法”更能支撑 AI 编程民主化：用户不必懂程序设计，但系统能强制执行“这个 Agent 只能访问这些资源”。



### 3.6 接受“可信核心只占 10%”

AI 时代软件是异构的：胶水代码、UI、数据管道、模型调用、系统接口。



Ming 不需要覆盖 100%，只要成为那 10% 关键逻辑的默认验证层，就已经是基础设施级机会。



追求 100% 通用性，会与成熟生态正面竞争，并被迫放宽严格性，最终失去差异。



## 4. 能力升级总路线
基于现有积累：



v1.0.0-rc.1；



1650 项测试全绿；



已有效果系统；



已有跨函数契约摘要；



已有 --proof-report；



已有 WASM 分层与 C 后端。



升级不需要推倒重来。建议按三个梯队推进：



第一梯队：让“证明”成为可独立消费的协议；



第二梯队：Agent 原生交互 + 参数化效果；



第三梯队：生态化与标准化。



## 5. 第一梯队：让“证明”成为可独立消费的协议
目标： 把 --proof-report 从 Ming 自己的报告格式，升级为外部工具和 Agent 可以独立复核的标准对象。



准入条件： v1.0 稳定版发布后立即启动。



### 5.1 证明对象标准化输出

工作项：



新增 --proof-format smt-lib 选项，将每个函数的验证条件（VC）输出为 SMT-LIB 2.0 格式；



对已证明义务，可选输出 Alethe 格式的证明日志，使证明可被独立证明检查器复核；



在 --json 诊断协议中增加 proof\_obligation\_id 和 solver\_status 字段，使每条诊断可追溯到具体 VC。



交付物：



docs/proof-protocol.md 规范文档；



ming check --proof-format smt-lib 可用；



至少一个外部 SMT 求解器（Z3）能消费 Ming 输出的 VC 并独立返回 unsat / sat。



优先级： P0。



### 5.2 契约桥 MVP：从 TypeScript / Python 提取契约

工作项：



实现 ming bridge extract 子命令；



从 TypeScript 的 JSDoc 注解或 Python 的类型注解 + docstring 中提取前置/后置条件候选；



生成 Ming 契约桩（.mingi 接口文件）；



生成物是契约声明：requires / ensures 签名 + 类型映射；



Ming 编译器用这些桩对跨语言调用点做契约一致性检查；



首批只支持一种源语言和一种边界形态。



交付物：



ming bridge extract --from ts --to ming 可用；



一个 TypeScript 函数 + Ming FFI 调用的端到端示例，Ming 能报告契约是否被满足。



优先级： P0。



## 6. 第二梯队：Agent 原生交互 + 参数化效果
目标： 让 Agent 能以高带宽、低摩擦的方式与 Ming 的验证能力交互，同时把效果系统升级为可执行的安全策略。



准入条件： 第一梯队证明协议稳定，至少有一个外部消费者。



### 6.1 Agent 原生验证协议

工作项：



在现有 LSP 之上，增加一套 Ming Agent Protocol：



queryTypeContext：请求某个位置的类型和效果上下文；



getContractSummary：获取函数的 requires / ensures 摘要及当前证明状态；



submitCandidate：提交候选实现，返回契约验证结果 + 结构化失败原因（具体哪个 VC 未证，以及 SMT-LIB 形式的反例模型）；



requestProofObligation：请求特定函数的原始 VC，自行用外部求解器尝试。



所有消息 schema 公开，与 --json 诊断码体系对齐。



交付物：



协议规范文档；



参考 Agent 客户端（Python / TypeScript 最小实现）；



演示“Agent 提交候选 → Ming 返回 VC 和反例 → Agent 修正”的完整循环。



优先级： P1。



### 6.2 参数化效果系统

工作项：



当前效果是 fs / net 等无参数名称。升级为带参数的效果表达式：



ming

with fs("/data/\*\*")

with net(host = "api.example.com", scheme = "https")

with exec(allow = \["git", "make"])

规则：



效果传播规则：调用方声明必须覆盖被调方声明的参数范围；



编译器检查包含关系；



运行时强制：在 VM / WASM / C 后端中，效果参数传递给宿主环境，由宿主执行实际能力边界。



交付物：



参数化效果语法和类型规则；



至少在 C 后端和 WASM 宿主中实现 fs 参数的范围检查；



一个演示“Agent 生成的代码只能访问指定路径”的端到端示例。



优先级： P1。



## 7. 第三梯队：生态化与标准化
准入条件： 前两个梯队已经产生外部消费者。至少有一个外部项目或 Agent 框架实际使用了 Ming 的证明协议或契约桥。



### 7.1 契约层的 WASM Component Model 对齐

工作项：



将 Ming 的跨语言契约桩映射为 WIT（WebAssembly Interface Types）接口定义；



Ming 编译为 WASM component 时，导出的契约信息与 WIT 接口双向可对应；



任何支持 Component Model 的宿主都能发现和消费 Ming 验证过的契约，而不需要知道 Ming 语言本身。



交付物：



WIT 映射规范；



一个 WASM component 示例，宿主能读取 Ming 导出的契约。



优先级： P2。



### 7.2 证明缓存与增量验证

工作项：



将每个函数的证明结果（VC 哈希 + 求解器证明日志）作为内容寻址的证明工件缓存；



当函数体或依赖契约哈希未变时，跳过重新求解；



当 Agent 只修改非契约相关代码时，验证延迟接近零。



交付物：



证明缓存格式规范；



增量验证基准测试。



优先级： P2。



## 8. 优先级总表
优先级	工作项	依赖	估计周期

P0	证明对象 SMT-LIB / Alethe 输出	无	2–3 个 minor 版本

P2	证明缓存	证明协议稳定 + 真实使用反馈	v2.0 阶段

## 9. 一条关键边界：核心严格性不妥协
在上述所有升级中，Ming 语言本身的核心严格性不要妥协：



不因为要“支持更多生态”而引入隐式转换；



不放宽值语义；



不取消效果门禁；



不允许静默失败。



Ming 的护城河恰恰来自这些“不妥协”。一旦为了通用性稀释它们，就失去了作为“可信验证层”的差异化价值。



外部多样性由契约桥和 WASM component 承接。



Ming 核心始终保持：



可证明、可审计、不可静默失败。

## 11. 总结
AI 编程需要任务通用性，但不需要单一语言承担；



Ming 不做用户的唯一语言，而做 AI 生成代码背后的可信验证与编排层；



用户可以不写 Ming，甚至不知道 Ming 存在；



Ming 的通用性体现在“能被任何语言、任何任务、任何 Agent 调用”；



发展重点：证明协议标准化、契约桥、Agent 原生交互、参数化效果、WASM 契约对齐、证明缓存；



核心严格性不妥协，外围生态通过契约桥与 WASM component 接入。



Ming 的目标不是成为下一个 Python，而是成为 AI 时代软件基础设施中的可信验证层。
