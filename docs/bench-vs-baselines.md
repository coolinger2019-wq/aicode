# 跨语言基准对比（T5.1：v0.93 交付；数据采集于 v0.92——两版对本任务集零语义差异）

> **本文件在 docs/ 观测文档族中的位置**：`docs/capabilities.md` 管"能不能做"（能力矩阵），`docs/support-matrix.md` 管"哪个后端支持哪种形态"（机器可验证矩阵），`docs/opt-baseline.md` 管"VM 内部机制统计"（MING_STATS 指令/深拷贝/分配计数，O0 优化对照锚），`docs/coverage-baseline.md` 管"测试覆盖率"，`docs/serve-observation.md` 管"服务端吞吐"。**本文只管一件事：Ming 与其他语言在同一台机器、同一批任务上的性能对比。**
>
> 数据源：`tests/bench_vs/results.json`（由 `tests/bench_vs/run.mjs --write` 机械生成，含环境指纹、逐腿 5 次原始值与验证 token 口径；手工改数字会被下次复跑暴露）。配套耗时锚点：`tests/bench.baseline.json`（回归锚，口径不同，见 §8 交叉核对）。
>
> **一句话立场**：本报告存在的前提是"性能诚实度"是北星第三支柱——Ming 赢的项和输的项必须同样显著地写在同一张表里；只发布好看的数字等于没发布。

## 1. 目的

回答一个真问题：**性能是否构成采用 Ming 的障碍？**

Ming 的北星论点有三根支柱：AI 写 Ming 更少出错（T1 对照实验验证）、效果系统即安全边界（污点/门禁）、以及**性能必须诚实可查**。性能不是 Ming 的卖点——它的卖点是显式、值语义、机器友好——但"慢多少"必须是一句任何人可以自己复跑验证的话，而不是一句营销话术。

本报告把 Ming 的三档引擎（tree 参考实现 / 默认 `ming run` 即 VM+wasm 分层 / C 原生后端 cc）与 Node 24、Python 3.10、C（gcc -O2）放在同一台机器、同一批 7 项任务上对比，逐项给出事实性结论。**结论只有三态：快、慢、不确定；输的项照发。**

## 2. 方法学

- **同机同任务**：全部语言在同一台机器（环境指纹见 §3）顺序执行同一批 7 项任务；每种语言的任务实现语义等价（同一输入、同一输出；harness 每次运行都做验证 token 数值比对，任何不一致该腿标 fail、不进统计）。
- **min-of-5**：任务 1–6 每项每腿预热 1 次 + 正式 5 次，取最小值。取最小值而非平均/中位，是为了压掉后台噪声对"能力上限"的干扰——min 接近该项在该机器上的真实可达耗时；代价是它不反映典型负载下的方差（见 §6.1 波动记录与 §7 局限）。
- **内部计时口径（任务 1–6）**：计时点在**程序内部**（主任务开始执行到结束），**排除解释器/运行时启动开销**——Ming 用 `std.time.monotonic_ms`（**1ms 整数分辨率**——低于 1ms 的差异不可分辨，6ms 级读数的真值 ∈ [6,7) 区间），JS 用 `performance.now`（亚毫秒），Python 用 `time.perf_counter`（亚毫秒），C 用 `QueryPerformanceCounter`（亚毫秒）。这样测的是"跑起来之后"的执行性能，四语言同口径（分辨率不同——亚毫秒级任务的跨语言对比以量级为准）。
- **启动项整进程墙钟（任务 7）**：例外是启动时间——它测的恰恰是**从进程拉起到退出的整段墙钟**（由 harness 计，含解释器启动、CLI 初始化、AOT 产物加载）。没有这一项，"Ming 用起来快不快"就只剩一个被内部口径掩盖的答案。
- **ming cc 腿特殊口径**：自测计时的 Ming 程序不达 cc 资格（monotonic_ms 形态触发 C1 "let 推导 null" 具名拒绝——非专用 time 效果闸门；`std.time.monotonic_ms` 触发 C1 具名拒绝），无法程序内自测 → cc 腿计时 = harness 测 **exe 整进程墙钟**，与自测口径差 ≈ 进程启动（本机空 exe 墙钟 10.65ms，见 §5.2）。**cc 列与自测口径列不可直接互比**，表内以 † 标注。
- **数据流**：`node tests/bench_vs/run.mjs --write` → `tests/bench_vs/results.json`（含环境指纹与逐腿原始值）→ 本文表格由该文件填数。复跑命令见 §9 读数指南。

## 4. 口径声明（先读再比）

逐条如实声明，每条都是"不这么写就会误导"的口径：

1. **C 腿 HOF = 循环等价**：C 标准库没有高阶函数/闭包，"HOF 链"这一项的 C 实现**不是**"用 C 实现一套 HOF 机制"，而是语义等价的平铺循环（map(+1)→for 累加生成、filter(偶数)→条件收集、fold→求和循环）。它测的是"C 手写循环能多快"，不是"C 的 HOF 抽象能多快"——C 腿在这一项上是**任务等价**而非**机制等价**，与 Ming/Node/Python 的倍数对比要带着这个前提读（同理：词频项的 C 腿哈希表是手写开放寻址表，FNV-1a，零第三方）。
2. **C 腿 JSON = N/A**："10MB JSON 解析"项 C 腿不比。理由：本仓库纪律是**零第三方依赖**（硬规则 3），C 侧没有自带 JSON 解析器；手写一个 JSON 解析器是另一个量级的任务（等同把"解析器实现"混进"JSON 处理性能"），引入 json-c 等外部库则破坏零依赖口径。两项都不做，如实标 N/A，不用近似值冒充。
3. **Python 3.10.11 vs plan 3.12**：T5.1 立项文本写的是 Python 3.12，本机可用的解释器是 3.10.11。选择"装 3.12"还是"如实用 3.10 并登记偏差"，本项目选后者——伪造环境版本比版本偏差本身危害大。CPython 3.11 相对 3.10 有约 10–25% 的解释器提速（视负载），意味着 **Python 列的数字对 Ming 偏"有利"**，读表时须知。
4. **内存列缺失（Windows 受限）**：T5.1 立项要求"记录内存"。Windows 上跨语言统一进程内存口径没有干净的零依赖实现：harness 尽力而为只采到了 **JS 腿自报 RSS**（`process.memoryUsage().rss`，如 jsonparse 腿 85.7MB，原始值在 results.json 的 `memBytes` 字段可查）；Python 的 `resource` 模块 Windows 不可用；C/Ming 无标准口径。**单语言内存数字没有跨语言对比意义，本表不发布内存列**——缺这一列是如实缺，不是忘了。
5. **"Ming 相对倍数"的定义与标注规则**：倍数 = **Ming 默认腿（`ming run`，VM+wasm）耗时 ÷ 对照语言耗时**。>1 表示 Ming 慢 N 倍，<1 表示 Ming 快。本表 6 项算法任务中 Ming 最快腿恰均为默认腿（tree 恒更慢、cc 不可用或墙钟口径不可比），故"最快 = 默认"。标注规则沿用 T1 对照实验的预注册判据（plan §4.15.3：相对差 >20% 记"显著"）：**≥20% 差距标 ✅ 快 / ❌ 慢；±20% 以内标 ≈ 持平**——机械规则，防选择性标注。
6. **"Ming VM"列的真实口径 = 默认引擎（VM+wasm 分层）**：harness 的 `ming-vm` 腿是**不带 `--no-wasm` 的默认 `ming run`**。wasm 资格逐项事实：fib/loopsum 两项 harness 注记 MING_WASM_DEBUG=1 实测 wasm 资格 OK（数值热点真实经 wasm）；HOF 项按 harness 注记闭包链回落 VM（62ms 是 VM 解释器口径）；词频/JSON/文件扫描三项经本报告作者用 MING_WASM_DEBUG=1 复核，wasm 模块编译存活无 REJECT，但热点含宿主导入（Map/Json/fs 操作走宿主桥）。**本表没有纯 VM（`--no-wasm`）腿**——需要该口径用 `tests/bench.mjs` 或自行加跑。因此 Ming 列应读作"默认体验"，不读作"纯 wasm 上限"或"纯解释器下限"。
7. **cc 资格面是硬约束**：7 项任务中 cc 腿只有 2 项可用（fib/loopsum，且需要专用 cc 变体程序——main 带 time 效果即 C1 拒绝）。其余 5 项 N/A，真实拒绝原因（results.json 原文）：HOF = `C1 不支持该程序形态:空 Vec 字面量`；词频 = `C1 不支持该程序形态:let 标注 Vec(C2 仅数值/str/Vec[i64])`；JSON = `C1 不支持该程序形态:块尾表达式(unit 返回 Match)`；文件扫描 = `C1 不支持该程序形态:let 推导 null`。**"cc 能救性能"的适用面比表上的速度数字更值得先看。**
8. **快照非承诺**：本表所有数字是 **2026-11-20 单机快照**。Ming 侧的性能是当前实现的结果，不是语言的理论上限（O1+ 优化 pass 未落地，见 plan §4.16；值语义深拷贝成本见 §8 opt-baseline 互引）；Node/Python/C 侧同样只是当前版本本机配置的结果。**任何数字都不构成性能承诺**（稳定性契约将性能数字列入非承诺面）。

## 6. 结论（三态纪律）

### 6.1 逐项事实结论

- **fib(24) 递归**：Ming 默认腿 6ms ≈ Python（6.39ms，差 6% < 20% 不显著）；慢 Node 11×；慢手写 C 约 107×。cc 变体墙钟 14.2ms，扣除进程启动（空 exe 10.65ms）后计算段差值法粗估 ≈3.5ms——比手写 C（0.056ms）仍慢约 63×：C 后端产物带 Ming 运行时包装，不是裸 C。
- **循环累加 100 万**：Ming 默认腿 6ms，**快 Python 6.5×**；慢 Node 2.9×、慢 C 约 27×。cc 变体墙钟 10.6ms 与空 exe 启动（10.65ms）同档——此项 cc 计算段（<1ms）被启动噪声淹没，与手写 C 无显著差。
- **HOF 链 10 万元素**：Ming 62ms（闭包链回落 VM 解释器，§4.6），**慢 Node 31×、慢 Python 7.1×**——本表 Ming 输得第二重的项。C 腿 0.022ms 是循环等价（机制不等价），与 Ming 相差三个数量级但不可直接比。cc N/A。
- **词频统计 2 万词**：Ming 18ms，**慢 Node 21×、慢 Python 14×**——本表 Ming 输得最重的项（`Map[str,i64]` 哈希计数逐操作经解释器/宿主桥；Node 的对象属性计数走 V8 JIT 内联）。cc N/A（C2 白名单外）。
- **10MB JSON 解析**：Ming 238ms（tree 239ms——解析主体是**宿主内建 json.parse（纯 JS 手写解析器 parseJsonText，tree/VM 共用同一宿主代码，计时段内无 Ming 级解释执行——这才是 tree ≈ vm 的原因）**；Ming 侧数字 = 宿主 JS 解析器 + Ming 值包装/污值包装，**慢 Node 5.9×**（V8 原生 `JSON.parse`）、**慢 Python 2.4×**。Ming 侧额外走污值路径（`Untrusted[str]` → parse → `Untrusted[Json]` → 投影表消费）——这是安全语义的成本，如实计入。C N/A。
- **1k 文件扫描**：Ming 97ms，慢 Node/Python 约 1.26×、慢 C 1.48×。I/O 主导任务四语言收敛（65–97ms），解释器开销不再是主导项；注意 1.26× 恰在 20% 显著阈值边缘（见 §6.2 波动注记），档位归属对噪声敏感。
- **启动时间**：ming CLI 67.7ms ≈ Node 61.8ms + 6ms（vs Node +9.7% 不显著；vs Python 慢 1.69×）；AOT 缓存命中的工具运行 91.8ms（vs Node 慢 1.49×，含真实 wc 工作）；C exe 10.65ms 是所有启动数字的下界。

### 6.3 汇总：性能是否构成采用障碍？

只陈述数据支持的判断：

1. **纯计算、wasm 分层覆盖不到热点的形态（HOF/词频）**：Ming 默认腿慢 Node 21–31×、慢 Python 7–14×。这是本表最大的实际性能代价，构成此类场景的真实成本。
2. **数值热点经 wasm 的形态（fib/循环累加）**：Ming 默认腿与 CPython 同档（fib ≈持平）或更快 6.5×（循环累加）；对 Node JIT 仍慢 3–11×，对手写 C 慢 27–107×。wasm 分层把"解释器档位"抬到了"脚本语言档位"，但没到"原生档位"。
3. **I/O 主导任务（1k 文件扫描）**：差距收窄到 1.26–1.48×；系统调用与启动主导，语言档位差异被稀释。
4. **JSON 解析（含污点语义成本）**：慢 Node 5.9×、慢 Python 2.4×。安全语义（污值投影）有可测成本，如实计入。
5. **启动档位**：ming CLI 与 node 同档（+6ms）；比 Python 慢 1.7×；AOT 缓存使命中路径可用（91.8ms 完成一次真实工具运行）。
6. **cc 后端**：资格内两项（fib/loopsum）的墙钟与原生 C 同档（启动主导）或差个位数毫秒；但**资格面窄（7 项中 5 项 N/A）是比单腿速度更大的实际约束**——"用 cc 获得原生速度"目前只对数值纯函数形态成立。

对"是否构成采用障碍"的回答（分场景，数据支持的边界内）：
- 对 **CPU 密集、cc 资格外**的形态（HOF/词频类）：慢 Node 21–31× 是实际代价；是否构成"障碍"取决于场景延迟敏感度——数据不给价值判断。
- 对 **脚本/文本/数值混合**场景：与 Python 互有胜负（-6% 到 +14×），未显示对 Python 用户的一致劣势。
- 对 **北星场景（CLI 安全工具：日志/文件/内网服务）**：本表 I/O 项差距 1.26×、启动同档 node、cc 数值形态近原生——**数据显示性能在该场景不构成主要障碍**；主要代价出现在容器/闭包/哈希密集的纯计算段。
- **不确定**：真实混合 workload 的表现（本表是 7 项微基准，非端到端应用）；wasm 资格扩面后（宿主导入面继续收窄）；O1+ 优化 pass 落地后（值语义深拷贝成本可被消除的份额，见 §8 opt-baseline 互引）；spawn 并行场景本表未测。以上均不外推。

## 7. 局限

- **单机单日**：一台消费级桌面（i5-12600K）、一个 OS（Windows）、一天内两轮采集。数字对**本机**负责；换 CPU 代际、换 OS、换 Node/Python 版本，数字会变，且变化方向不承诺。
- **禁止外推**：本报告不支持"Ming 在你的机器上快/慢 N 倍"的换算。复跑命令是公开的（§9），想知道自己机器上的数字就自己跑——这比相信任何转述都可靠。
- **任务集构造偏差**：7 项任务由 Ming 项目作者设计（与 T1 对照实验同源的任务构造偏差风险）。fib/循环/HOF 这类微基准偏"纯计算"，对真实程序（I/O 密集、大量 FFI、GC 压力形态）代表性有限；文件扫描/启动项更接近真实使用，权重应据此理解。
- **min-of-5 的口径代价**：min 压噪声但也压掉了方差信息。两轮独立采集 >15% 的项已在 §6.2 如实列出（1/36）；不做统计显著性宣称（与 T1 同纪律）。
- **内存列缺失**（§4.4）：跨语言内存对比本版没有可靠口径，不发布。
- **快照非承诺**（重申 §4.8）：数字随版本演进会变，O1+ 优化 pass 落地后本表应刷新；旧表不追改，新表覆盖。
- **样本规模**：每格 5 次取 min，不是 30 次取分布。本表能回答"这台机器上谁快谁慢"，回答不了"快慢是否统计显著"。

### 8.2 与 docs/opt-baseline.md 的机制互引（解释 VM 档位慢在哪）

opt-baseline 的 MING_STATS 统计（steps/deepCopy/alloc/callMethod）解释本表 Ming 慢的**机制**，本文不复述其计数细节，只引结论：

- **HOF 项慢 31× 的机制**：HOF 链 vm-only 腿 steps 254 万、callMethod 10 万次、deepCopy 32 万次、alloc 31 万——每次闭包调用经 CALLMETHOD 派发、Vec 载荷深拷贝；对照 Node 的 map/filter/reduce 是 JIT 内联的原生循环。**解释器逐指令 + 值语义深拷贝**是差距的主要成分（opt-baseline 的 HOF 程序与本表是同族不同常量，机制结论同构）。
- **值语义成本的一般底座**：拷贝密集 10 万绑定 deepCopy 270 万次 / 10 万迭代（opt-baseline 表）——Ming 值语义的固有成本不在本表 7 项中，但它是"绑定/容器密集程序在 Ming VM 档位慢"的机制解释；O2 拷贝消除 pass（plan §4.16）落地前，本表数字可视为该机制的下游表现。
- **JSON 项与引擎档位无关**：本表 jsonparse tree 239ms ≈ 默认腿 238ms——解析主体是解释执行的 std json 实现，换引擎不改变瓶颈（与 §6.1 结论一致）。

## 9. 读数指南（如何复现）

```bash
# 1) 采集（写 results.json，含环境指纹与逐腿原始值；另打印控制台表格）
node tests/bench_vs/run.mjs --write

# 2) 只看 JSON 不落盘
node tests/bench_vs/run.mjs --json
```

- **逐项数字以你机器上的复跑为准**，本文表格只在"同机同版本"前提下可逐字对照；你复跑的 min 与本文 min 差异 >15% 的项属于机器/版本状态漂移，以你自己的 results.json 为准。
- harness 退出码：全部腿 ok 或 na → 0；出现 fail（验证 token 不一致/运行失败）→ 1，错误走 stderr。
- 回归锚另有其表：`node tests/bench.mjs`（Ming 三腿整进程墙钟，`--write-baseline` 刷新回归基线，加速比回退 >20% 打 WARN）——**它不产生跨语言数字**，不要拿 bench.mjs 的输出跟本文对照语言列比。
- harness 内部实现（验证 token、mulberry32 生成器复刻、cc 编译参数等）以 `tests/bench_vs/run.mjs` 头注为单一事实来源；本文不复述 harness 内部实现，防止两处漂移。
